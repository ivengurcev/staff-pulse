# Codex — контекст работы

Перед реализацией конкретного шага читать:

1. `docs/task.md` — исходное тестовое задание целиком.
2. `docs/steps.md` — границы этапов.
3. `docs/decisions.md` — уже принятые технические решения.
4. `docs/clarifications.md` — трактовки неоднозначных требований.
5. Файл текущего шага в `docs/steps/`.

## Общие правила

- Сначала изучить существующий репозиторий и относящуюся к текущему этапу документацию.
- Не пересоздавать уже работающую структуру.
- Не реализовывать будущие этапы заранее.
- Не обновлять major-версии зависимостей без явно зафиксированного решения.
- Не создавать git commit или tag без отдельной команды.
- Не придумывать требования, которых нет в `docs/task.md`, `docs/decisions.md`, `docs/clarifications.md` или файле текущего этапа.
- Если найдено противоречие между документами или кодом и утверждённым планом, остановиться и сообщить о нём до продолжения реализации.
- После изменений выполнить доступные проверки и сообщить их фактический результат.
- Не переходить к следующему этапу самостоятельно.

## Планирование и реализация

Каждый этап состоит из двух отдельных фаз: планирования и реализации.

### 1. Планирование

До начала реализации должны быть определены и зафиксированы все существенные технические и архитектурные решения текущего этапа.

На этапе планирования определяются:

- архитектура и границы модулей;
- модель данных;
- API-контракты;
- используемые зависимости;
- основные алгоритмы;
- структура и владельцы состояния;
- трактовки неоднозначных требований;
- границы текущего этапа;
- способы проверки результата.

Архитектурные решения принимаются до начала реализации и фиксируются в документации проекта.

Если в процессе планирования обнаруживается вопрос, способный повлиять на архитектуру, публичный интерфейс, модель данных, зависимости или следующие этапы, он должен быть разрешён до команды на реализацию.

### 2. Реализация

После утверждения плана задача Codex — реализовать согласованный план.

Во время реализации:

- не принимать новые архитектурные решения самостоятельно;
- не менять утверждённую архитектуру;
- не менять границы модулей без пересмотра плана;
- не добавлять существенные зависимости без пересмотра плана;
- не менять API-контракты или модель данных;
- не расширять scope текущего этапа;
- не реализовывать функциональность следующих этапов.

Если во время реализации обнаруживается, что утверждённого плана недостаточно, он противоречив или реализация требует нового архитектурного решения, остановиться и сообщить об этом. Не выбирать архитектурный вариант самостоятельно.

### Локальные детали реализации

Codex может самостоятельно выбирать только локальные, обратимые детали, которые:

- не влияют на архитектуру;
- не меняют публичное поведение;
- не меняют API или модель данных;
- не требуют новой существенной зависимости;
- не влияют на следующие этапы;
- легко изменить без переработки нескольких модулей.

Примеры допустимых самостоятельных решений:

- имя локальной переменной;
- имя приватного helper;
- порядок небольших внутренних функций;
- локальная реализация внутри уже определённого интерфейса;
- небольшая деталь разметки, не меняющая согласованный UX.

Если непонятно, является ли решение локальной деталью или архитектурным решением, считать его архитектурным и сообщить о недостатке плана.

## Переход между этапами

Codex не переключает текущий этап самостоятельно.

Переход выполняется только после того, как текущий этап:

1. реализован;
2. проверен;
3. прошёл ручное ревью;
4. при необходимости исправлен;
5. закоммичен;
6. получил соответствующий тег `step/N`.

После этого отдельно обновляются:

- раздел `Текущая задача` в этом файле;
- файл следующего этапа в `docs/steps/`;
- при необходимости `docs/decisions.md` и `docs/clarifications.md`.

Только после явного обновления контекста начинается планирование следующего этапа.
