# Staff Pulse — уточнения и assumptions

Этот файл хранит наши трактовки мест, которые исходное ТЗ не определяет однозначно.

## Второй уровень открыт по умолчанию

Исходная формулировка:

```text
второй уровень открыт по умолчанию
```

Принятая трактовка:

```text
Division          раскрыт
    Department    виден
        Team      скрыт
```

То есть при первой загрузке видны корневые Division и их дочерние Department.

Department раскрывается пользователем, после чего становятся видны Team.

## Количество mock-узлов

ТЗ требует:

- минимум 40;
- минимум 3 уровня.

Для FOUNDATION принято:

```text
3 Division
12 Department
36 Team
```

Итого:

```text
51
```

## Источник данных

Mock-данные должны быть детерминированными.

Случайные значения при каждом запуске не использовать, чтобы:

- UI был воспроизводим;
- тестирование было предсказуемым;
- будущие realtime-изменения было проще отличать от начального состояния.

## Client/server types

Не использовать общий TypeScript-тип как замену runtime-проверке ответа.

Server может иметь свой `OrgNode`.

Client получает `unknown`, валидирует Zod и выводит тип из клиентской схемы.

Причина: это сохраняет реальную HTTP boundary.

## Tree state

`expanded` и другие UI-флаги не добавляются в `OrgNode`.

API-модель и UI-state разделены.

## Tree representation

Исходный массив API остаётся плоским.

Для отображения можно построить индексы:

```text
nodesById
childrenByParent
rootIds
```

Это подготовит данные к будущим patch-обновлениям без необходимости мутировать вложенное дерево.

## Performance indicator

Исходное ТЗ требует цветовой индикатор, но не задаёт пороги.

Пороговые значения являются implementation assumption.

Они должны:

- находиться в одном понятном месте;
- не считаться частью API-контракта;
- быть легко изменяемыми.

Цвет не должен быть единственным способом передачи значения.

## API URL

Client использует относительный путь:

```text
/api/org-tree
```

В development Vite proxy направляет его на Hono.

Причина: не связывать клиент с `localhost:3001` и сохранить ту же схему URL для будущего Nginx.

## Commit/tag policy

Можно делать промежуточные коммиты внутри этапа.

Тег:

```text
step/N
```

ставится только на коммит, которым этап действительно завершён.

## Документация

Документировать только то, что реально реализовано.

Не описывать CORE/POLISH/BONUS как готовые до их реализации.

Раздел «AI в разработке» должен отражать фактическую работу:

- что предложил AI;
- что было принято;
- что было изменено вручную;
- почему.
