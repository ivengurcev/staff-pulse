# Staff Pulse — уточнения и assumptions

Этот файл хранит наши трактовки мест, которые исходное ТЗ не определяет однозначно.

## Второй уровень открыт по умолчанию

Исходная формулировка:

```text
второй уровень открыт по умолчанию
```

Принятая трактовка:

```text
Division          раскрыт
    Department    виден
        Team      скрыт
```

То есть при первой загрузке видны корневые Division и их дочерние Department.

Department раскрывается пользователем, после чего становятся видны Team.

## Количество mock-узлов

ТЗ требует:

- минимум 40;
- минимум 3 уровня.

Для FOUNDATION принято:

```text
3 Division
12 Department
36 Team
```

Итого:

```text
51
```

## Источник данных

Mock-данные должны быть детерминированными.

Случайные значения при каждом запуске не использовать, чтобы:

- UI был воспроизводим;
- тестирование было предсказуемым;
- будущие realtime-изменения было проще отличать от начального состояния.

## Client/server types

Не использовать общий TypeScript-тип как замену runtime-проверке ответа.

Server может иметь свой `OrgNode`.

Client получает `unknown`, валидирует Zod и выводит тип из клиентской схемы.

Причина: это сохраняет реальную HTTP boundary.

## Tree state

`expanded` и другие UI-флаги не добавляются в `OrgNode`.

API-модель и UI-state разделены.

## Tree representation

Исходный массив API остаётся плоским.

Для отображения можно построить индексы:

```text
nodesById
childrenByParent
rootIds
```

Это подготовит данные к будущим patch-обновлениям без необходимости мутировать вложенное дерево.

## Performance indicator

Исходное ТЗ требует цветовой индикатор, но не задаёт пороги.

Пороговые значения являются implementation assumption.

Они должны:

- находиться в одном понятном месте;
- не считаться частью API-контракта;
- быть легко изменяемыми.

Цвет не должен быть единственным способом передачи значения.

## API URL

Client использует относительный путь:

```text
/api/org-tree
```

В development Vite proxy направляет его на Hono.

Причина: не связывать клиент с `localhost:3001` и сохранить ту же схему URL для будущего Nginx.

## Commit/tag policy

Можно делать промежуточные коммиты внутри этапа.

Тег:

```text
step/N
```

ставится только на коммит, которым этап действительно завершён.

## Документация

Документировать только то, что реально реализовано.

Не описывать CORE/POLISH/BONUS как готовые до их реализации.

Раздел «AI в разработке» должен отражать фактическую работу:

- что предложил AI;
- что было принято;
- что было изменено вручную;
- почему.

## CORE (step/2)

Трактовки неоднозначных мест исходного ТЗ для аналитической таблицы.

### Split-view vs переключатель

Исходное ТЗ: «Переключатель «Дерево / Таблица» или split-view при ширине ≥1280 px».

Трактовка:

- при ширине `>= 1280 px` — split-view (дерево слева, таблица справа, ~40/60);
- при ширине `< 1280 px` — переключатель «Дерево» / «Таблица», одновременно видно одно представление.

### Double-click semantics

Требование «двойной клик — обратная сортировка».

Трактовка:

- обычный клик по заголовку → ASC;
- double click по заголовку → DESC.

Дополнительных состояний сортировки нет; начальное состояние — без сортировки (порядок API).

### Фильтр применяется только к таблице

Требование не уточняет, фильтруется ли дерево.

Трактовка: фильтр по названию влияет только на таблицу. Дерево остаётся полным.

### Агрегаты до фильтрации

Агрегаты всегда вычисляются по полному snapshot; фильтрация не изменяет значения агрегатов.

### Нулевой headcount

Если суммарный headcount узла и потомков равен нулю, средняя эффективность неопределима.

Трактовка: `averagePerformance = null`, в UI отображается `—`.

### Выбор строки не переключает вид на мобильной ширине

Требование «клик по строке выделяет узел в дереве» не говорит о смене представления.

Трактовка: на ширине `<1280` клик по строке НЕ переключает `viewMode`; предки раскрываются в фоне, пользователь остаётся в таблице.

### Направление синхронизации tree ↔ table

Требование «клик по строке выделяет узел в дереве» задаёт только направление table → tree.

Трактовка: на CORE `selectedNodeId` меняется только при клике по строке таблицы. Клик по узлу дерева сохраняет expand/collapse и не меняет `selectedNodeId`; обратной синхронизации tree → table на CORE нет.
